# Distributing MetalVJ

Two desktop assets, both built and attached to a GitHub Release by
`.github/workflows/release.yml`:

| Platform | Asset |
| --- | --- |
| Windows x86_64 | `MetalVJ-<version>-windows-x86_64.exe` |
| Linux x86_64 | `MetalVJ-<version>-linux-x86_64.AppImage` |

`<version>` is `[workspace.package] version` in `Cargo.toml`. The scripts read
it there; nothing hardcodes it. The release workflow refuses to build when the
tag disagrees with `Cargo.toml`.

## Cutting a release

1. Bump `[workspace.package] version` in `Cargo.toml` (and refresh
   `Cargo.lock` if the version appears in a package entry).
2. Commit.
3. Tag according to the channel convention below.
4. Push the tag: `git push origin v0.2.0`.
5. CI builds both platforms and creates the Release. Nothing else to do; the
   assets appear on the Release page.

To rebuild the assets for an existing tag (e.g. after a flaky runner), run the
workflow manually with `workflow_dispatch` and pass the tag. `release.yml`
replaces the assets of that Release.

## Tag and channel convention

| Tag | Channel | Release flag |
| --- | --- | --- |
| `v1.2.3` | stable / main | normal release |
| `dev-v1.2.3` | dev | `prerelease: true` |

Any other tag or branch push does not build a release. This convention is
documented at the top of `.github/workflows/release.yml`; keep the two in
step when it changes.

The updater selects the channel by tag prefix, so `dev-v*` builds are opt-in
and must never be presented as stable.

## Local builds

| Script | Host | Output |
| --- | --- | --- |
| `scripts/package-windows.ps1` | Windows + Rust (MSVC) | `dist/MetalVJ-<version>-windows-x86_64.exe` |
| `scripts/package-linux.sh` | Linux + Rust + dev packages | `dist/MetalVJ-<version>-linux-x86_64.AppImage` |
| `scripts/package.sh` | either (dispatches) | as above |

Both print a machine-readable last line:

```
SHA256 <hex>  <name>
```

## Why the AppImage is only built in CI

The Linux binary links ALSA (`listen`), X11/Wayland (winit, glutin) and GL.
It cannot be produced on the maintainers' Windows machine: there is no WSL
distribution, no Docker and no Linux toolchain there. `ubuntu-24.04` in the
release workflow is the delivery path. `scripts/package-linux.sh` is what that
job runs; running it locally requires a Linux host with:

```
pkg-config libasound2-dev libssl-dev libxkbcommon-dev libwayland-dev \
libx11-dev libgl1-mesa-dev libegl1-mesa-dev
```

`libfuse2` is **not** required: `appimagetool` is invoked with
`--appimage-extract-and-run`.

The AppImage tooling is downloaded at build time, never committed:

- `https://github.com/linuxdeploy/linuxdeploy/releases/download/continuous/linuxdeploy-x86_64.AppImage`
- `https://github.com/AppImage/appimagetool/releases/download/continuous/appimagetool-x86_64.AppImage`

Neither publishes a `.sha256` asset, so the digests are pinned in
`scripts/package-linux.sh`. The `continuous` tag moves; when upstream ships a
new build the checksum fails loudly. Re-run with
`METALVJ_REPIN_APPIMAGE_TOOLS=1` to print the new digest and update the
constant. Cached under `packaging/.cache/` (gitignored).

## The icon is a placeholder

There is no branding art in this repository. `packaging/icons/MetalVJ.png` is
generated by `packaging/make-icon.ps1` (pure `System.Drawing`, no dependency)
and is deliberately generic: a rounded dark tile with an aperture/play glyph
and corner ticks. It is **not** MetalVJ's identity. Replace it with real art
(same filename, 256x256 RGBA PNG) before a public stable release.

Consequences today:

- **AppImage**: the placeholder is embedded as `MetalVJ.png` and used by the
  `.desktop` file.
- **Windows**: `metal-dash.exe` carries **no** embedded icon or version
  resource. `Cargo.lock` contains neither `winres` nor `embed-resource`, and
  adding a build-dependency to `metal-dash` for a placeholder was judged not
  worth the build cost and lockfile churn. To add it later, either:
  1. add `embed-resource` as a `[build-dependencies]` of `metal-dash` with a
     `.rc` naming `packaging/icons/MetalVJ.png` as the icon and the workspace
     version as `FileVersion`/`ProductVersion`, or
  2. shell out to `rc.exe` + `mt.exe` from the MSVC Build Tools in
     `package-windows.ps1` (the icon `.ico` can be produced by
     `packaging/make-icon.ps1 -Ico`).

## Verifying a download

The updater checks sha256 before running anything. To do it by hand:

PowerShell:

```powershell
Get-FileHash .\MetalVJ-0.0.1-windows-x86_64.exe -Algorithm SHA256
```

Linux / macOS:

```bash
sha256sum MetalVJ-0.0.1-linux-x86_64.AppImage
```

Compare against the `SHA256` line in the build log for that release (CI prints
it from the packaging scripts). A mismatch means the file is not what CI built.

## What is not covered here

- macOS: no script, no workflow job. `docs/MULTIPLATFORM.md` lists it as
  planned and it needs a Mac.
- Android APK: `scripts/build-apk.sh`, separate from this release pipeline.
- Code signing: neither the Windows `.exe` nor the AppImage is signed.
